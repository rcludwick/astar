`iax-ysfdch`. Written 2026-09-06 against the deployed reference
implementations, after astar's first System Fusion transmissions to

## 1. Where the DCH lives

A YSF radio frame is 120 bytes: 5 sync, 25 FICH, **90 payload**. The payload
is five 18-byte blocks. What is inside a block depends on the FICH's DT field
(`YSFDefines.h`: `YSF_DT_VD_MODE1 = 0`, `YSF_DT_DATA_FR_MODE = 1`,
`YSF_DT_VD_MODE2 = 2`, `YSF_DT_VOICE_FR_MODE = 3`).

**V/D mode 2** — what every Yaesu radio sends as "DN", and what astar sends —
splits each 18-byte block as:

```
block b (18 bytes) = [ 5 bytes DCH ][ 13 bytes VCH ]
                       40 bits        104 bits
```

`YSFPayload.cpp:processVDMode2Data` gathers the five 5-byte DCH slots into one
25-byte buffer (`memcpy(p2, p1, 5U); p1 += 18U`), and
`processVDMode2Audio` walks the VCH from bit offset 40 in steps of 144. astar
already has the VCH half (`astar-codec/src/ysf.rs`, `vd2_vch`/`vd2_put_vch`);
this document is the other 40 bits.

The **Header** and **Terminator** frames do not use that split at all.
`YSFControl.cpp:writeNetwork` sends `YSF_FI_HEADER` and `YSF_FI_TERMINATOR`
frames through `processHeaderData`, which reads the payload in the
*Data FR mode* shape: nine bytes from each block for one 45-byte field, and
the other nine for a second. So a header frame carries **no voice** — its
whole 90 bytes are two 20-byte callsign blocks under FEC.

## 2. The coding chain

Identical for both shapes; only the widths change.

```
plaintext  ──XOR whitening──►  ──append CRC-16──►  ──zero tail byte──►
   ──rate-1/2 convolutional──►  ──dibit interleave──►  scatter into blocks
```

**Order matters and is easy to get backwards: the whitening is applied
first, and the CRC is computed over the *whitened* bytes.**
`YSFPayload.cpp:processVDMode2Data` shows both directions in one function —
on the way in it does `checkCCITT162(output, 12U)` and only then
`output[i] ^= WHITENING_DATA[i]`; on the way out it re-XORs, then
`addCCITT162(output, 12U)`.

| Stage | VD mode 2 DCH | Header / Data FR |
|---|---|---|
| plaintext | 10 bytes | 20 bytes |
| whitening | `WHITENING_DATA[0..10]` | `WHITENING_DATA[0..20]` |
| CRC-16 | over 12 bytes (10 + 2) | over 22 bytes (20 + 2) |
| tail | byte 12 = `0x00` | byte 22 = `0x00` |
| convolutional | 100 input bits → 200 | 180 input bits → 360 |
| interleave | `INTERLEAVE_TABLE_5_20` | `INTERLEAVE_TABLE_9_20` |
| on the air | 25 bytes → 5 per block | 45 bytes → 9 per block |

**Whitening.** `WHITENING_DATA` in `YSFPayload.cpp` is twenty bytes:
`93 D7 51 21 9C 2F 6C D0 EF 0F F8 3D F1 73 20 94 ED 1E 7C D8`. It is not
magic — it is 160 bits of the PN9 sequence `x^9 + x^5 + 1` run from state
`0b1_0010_0111`, most significant stage out first, which is how
`astar-codec` already derives it for the VCH scrambler. astar generates it,
and a test asserts the generated bytes are the published ones.

**CRC.** Polynomial `0x1021`, init `0x0000`, unreflected, final XOR `0xFFFF`,
stored high byte first — `CCRC::addCCITT162`, and exactly the CRC
`astar-ysf`'s `crc` module already implements for the FICH.

**Convolutional code.** Rate 1/2, constraint length 5, generators
`1 + D^3 + D^4` and `1 + D + D^2 + D^4` — `YSFConvolution.cpp:encode` computes
`g1 = d + d3 + d4` and `g2 = d + d1 + d2 + d4`. That is bit-for-bit the coder
`astar-ysf`'s `conv` module already carries for the FICH, so the DCH reuses it
rather than growing a second one. The single zero tail byte is what flushes
the four memory bits so the decoder can finish in the all-zero state.

**Interleave.** Both published tables are the same rule at two widths, and it
is the same rule the FICH uses: write down the columns, read across the rows,
moving **dibits** (bit pairs), so the table entry is a bit index that is
always even. `INTERLEAVE_TABLE_5_20` is `0, 40, 80, 120, 160, 2, 42, …` —
five columns of twenty — i.e. entry `i` is `(i / 5) * 2 + (i % 5) * 40`.
`INTERLEAVE_TABLE_9_20` is nine columns of twenty: `(i / 9) * 2 + (i % 9) * 40`.
(The third table in that file, `INTERLEAVE_TABLE_26_4`, belongs to the VCH and
is the exception that moves single bits, which is why the file comments it.)
astar writes the rule, not the table.

## 3. What goes in each frame

### Communications frames: one DCH per frame, selected by FN

`YSFPayload.cpp:processVDMode2Data` switches on `fn`, and
`DroidStar`'s `ysf.cpp:encode_dv2` fills the same slots on transmit:

| FN | 10 bytes | MMDVMHost | DroidStar sends |
|---|---|---|---|
| 0 | destination | stored as `m_dest` | `**********` |
| 1 | source | stored as `m_source` | the station callsign |
| 2 | downlink | overwritten with `m_downlink` unless `gateway` | the station callsign |
| 3 | uplink | overwritten with `m_uplink` unless `gateway` | the station callsign |
| 4 | REM1 + REM2 | ignored | ten spaces |
| 5 | REM3 + REM4 | ignored | ten spaces |
| 6 | DT1 | dumped only | an FT-70D radio-ID constant |
| 7 | DT2 | dumped only | (unreachable, see below) |

`**********` is the wire's "unaddressed": `pYSFReflector3`'s `YSFReflector`
treats `m_dest == '**********'` as absent and falls back to the `YSFD`
header's destination, and its serial-number blacklist explicitly skips it.

**FN runs 0..6 with FT = 6, not 0..7.** `DroidStar`'s `encode_dv2` computes
`fn = (m_txcnt - 1U) % 7U` and calls `setFT(6U)`; its `case 7` is dead code.
FT is a *total*, so the last frame of a superframe is the one where FN == FT —
`pYSFReflector3` relies on exactly that (`if ((FN == FT) and ...)` closes its
GPS accumulation). A client that sends FN = FT = 0 forever, as astar did,
never produces the FN 0 and FN 1 frames a receiver takes the callsigns from,
even if the DCH were valid.

astar sends ten spaces for FN 6 rather than DroidStar's hard-coded FT-70D
radio-ID block. That constant identifies a specific Yaesu handheld; astar is
not one, has no GPS, and copying someone else's device signature onto the air
would be a false statement about what transmitted. A blank DT1 still checks
its CRC and simply yields no coordinates.

### Header and Terminator frames: CSD1 and CSD2

`YSFPayload.cpp:writeHeader(data, csd1, csd2)` is
`writeDataFRModeData1(csd1)` + `writeDataFRModeData2(csd2)`: the first
20-byte block goes into bytes 0..9 of each of the five 18-byte blocks, the
second into bytes 9..18.

* **CSD1** = destination (10) + source (10). `pYSFReflector3`'s
  `ysfpayload.processheaderdata` reads `output[0:10]` into `m_dest` and
  `output[10:20]` into `m_source`, which pins the order.
* **CSD2** = downlink (10) + uplink (10). Same file, `writeHeader` is called
  with `csd2 = m_downlink.ljust(10) + m_uplink.ljust(10)`.

`DroidStar`'s `encode_header` builds `csd1 = "**********" + callsign` and
`csd2 = callsign + callsign`, and uses the same routine for the terminator
(`encode_header(1)` with `FI = YSF_FI_TERMINATOR`). astar does the same.

### The FICH a softclient sets

`DroidStar`'s `encode_header`/`encode_dv2`, field by field
(bit positions from `YSFFICH.cpp`):

| Field | Value | Where |
|---|---|---|
| FI | Header / Communications / Terminator | `raw[0] >> 6` |
| CS | **2** | `raw[0] >> 4 & 3` |
| CM | 0 (`YSF_CM_GROUP1`) | `raw[0] >> 2 & 3` |
| BN, BT | 0, 0 | `raw[0] & 3`, `raw[1] >> 6` |
| FN | 0..6, cycling | `raw[1] >> 3 & 7` |
| FT | **6** | `raw[1] & 7` |
| Dev | false | `raw[2] & 0x40` |
| MR | 0 (`YSF_MR_DIRECT`) | `raw[2] >> 3 & 3` |
| VoIP | false | `raw[2] & 0x04` |
| DT | 2 (`YSF_DT_VD_MODE2`) | `raw[2] & 3` |
| SQL | false | `raw[3] & 0x80` |
| SQ / DG-ID | 0 | `raw[3] & 0x7F` |

VoIP is false on a client: `YSFControl.cpp:writeNetwork` is the code that
*sets* VoIP true, and it does so when a repeater is putting network audio back
on the air, which is not what a softclient is doing.

CS was the one field astar's `Fich` did not model — its bits were written as
zero. It is now `call_sign_path`, defaulting to 2 as a softclient sends.

## 4. The operational answer: why KC-Wide showed nothing

Three separate mechanisms, all of which astar tripped, and none of which is
the reflector's own last-heard.

**(a) A reflector's last-heard is NOT the reason.** `pYSFReflector3` takes the
talker from the `YSFD` header — `tx[3] = data[14:24]` — which astar has always
filled correctly, and `YSFNetwork.cpp` writes those same three 10-byte fields.
So "astar's callsign never appeared" cannot be explained by the DCH alone on a
plain YSFReflector dashboard, and this is worth saying because it is the
obvious wrong answer.

**(b) The attribution and the DCH regeneration both stop at a failed CRC.**
`YSFControl.cpp:writeNetwork` — the code in every MMDVM hotspot and repeater
between the reflector and a Yaesu radio — does:

```
case YSF_FI_HEADER:        ok = processHeaderData(...);   if (ok) processNetCallsigns(...)
case YSF_FI_COMMUNICATIONS: ok = processVDMode2Data(fn);  if (ok) processNetCallsigns(...)
```

`processVDMode2Data` returns `ret && (fn == 0U || fn == 1U)` — it is *only*
true for a DCH that passes its CRC **and** sits in frame 0 or 1. astar sent an
all-zero DCH in every frame, with FN pinned at 0, so `ret` was false every
time: `processNetCallsigns` never ran, and — the part that reaches the radio —
the block that rewrites the DCH with the repeater's own downlink/uplink
callsigns is inside `if (ret)`, so the zeroed DCH was passed to the air
unchanged. A Yaesu radio reading that has no callsign to display. This is the
mechanism the backlog entry guessed at, and it is real.

**(c) A reflector opens a *stream* on the header frame, and relays only while
one is open.** In `pYSFReflector3`'s `YSFReflector`, the `YSFD` branch creates
the stream record inside

```
if ((tx[0] == 0) and (id_corr != 0) and (FI == 0) and (SQL != 127) and ...)
```

and the loop that forwards the datagram to every other linked client is
guarded by `(id_corr == tx[0]) and (id_corr != 0)`. Until a frame whose FICH
decodes with **FI == 0** opens the stream, `tx[0]` is zero and *nothing is
relayed anywhere*. astar did send one FI = Header frame — but with a voice
payload where the CSD belongs, so `processheaderdata` failed
("Error processing HC data", "Stream opened with invalid HC") and the
dashboard's `dst/src/uplink/downlink` line came back empty even where the
stream did open.

**(d) KC-Wide's monitor is not a YSF reflector dashboard.**
`level.kansascitywide.com` serves a page titled "KCWide Audio Monitor" — a
custom WebSocket audio monitor with an "Active Station" callsign, a live
meter and a scope. It reports whoever the **bridge** attributes, which is the
`processNetCallsigns` path in (b), not the reflector's own `YSFD` log. That is
consistent with astar's M17 overs appearing and its YSF overs not: M17 carries
its callsign in the stream itself, where a YSF over's callsign, for anything
downstream of the reflector, comes out of the DCH.

**One sentence.** astar's over carried an all-zero data channel and a FICH
pinned at FN = FT = 0, so every reference receiver's DCH CRC check failed —
`processNetCallsigns` was never reached and the DCH was never regenerated —
and the audio travelled with nothing downstream able to say who sent it.

## 5. What is fixed, and what only a radio can settle

`astar-ysf`'s new `dch` module encodes and decodes both shapes, and
`astar-console`'s YSF transmit path now sends a real Header frame at
key-down, cycles FN 0..6 with FT = 6 filling each frame's DCH, and closes
with a real Terminator. The FICH carries CS = 2 and the rest as the table in
§3 says.

Round trips, known-answer vectors against the published tables, and the
loopback parrot are all in the test suites. What they cannot settle is
whether a Yaesu radio shows the callsign — that needs Rob, a radio, and a
live reflector, and it stays open in `iax-ysfdch` until it happens.
