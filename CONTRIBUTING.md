# Contributing to astar

Thanks for looking. astar is early — `0.1.0beta`, never released — so the most
useful contributions right now are bug reports from real radios and real
networks, and fixes with a test attached.

## Licence: inbound = outbound

astar is **AGPL-3.0-only**. By contributing you agree that your contribution is
licensed under the AGPL-3.0-only, under the same terms as the rest of the
repository. There is no CLA and no copyright assignment.

Every new source file gets the standard three-line header — this is what the
existing files carry, and consistency here is what makes the licence
unambiguous at the file level:

```
// astar — Copyright (c) 2026 Rob Ludwick.
// SPDX-License-Identifier: AGPL-3.0-only
// Licensed under the GNU Affero General Public License v3.0 only. See LICENSE.
```

Use the comment syntax of the language (`#` for shell, justfile and Python).

**Do not add the AGPL header to `vendor/ambe-thumbdv`.** That directory is an
MIT/Apache-2.0 island with its own licence files, and relicensing it by
accident is a real hazard — see its `VENDORED.md` before touching anything in
there. The same goes for the Inter font files under `apps/gui/assets/fonts`
and the vendored C libiax2 under `harness/`.

If you are proposing to add a dependency, check its licence is AGPL-compatible
first. Anything that cannot be distributed under the AGPL does not belong in a
shipped crate.

## Safety rules that are not negotiable

These are legal and physical constraints, not style preferences. A change that
weakens one will be rejected on sight.

1. **Never transmit on the air autonomously.** No test, script, CI job, tool or
   automated agent may key a transmitter or connect to a live node or
   reflector. Automated tests reach `127.0.0.1` and nothing else. Hardware
   suites stay behind `IAX_THUMBDV_TESTS=1`.
2. **A pinned ThumbDV port narrows the scan; it never replaces it.**
   `IAX_THUMBDV_PORT` filters the FTDI VID/PID candidate list. It must never
   become a way to hand the opener an arbitrary tty — opening a USB radio
   interface's serial port asserts RTS and keys a transmitter. There are tests
   guarding exactly this; keep them passing and keep them meaningful.
3. **The node daemon's remote-key path refuses while D-Star is active.** That
   guard keys off the feature-independent `dstar_active` snapshot flag rather
   than a `#[cfg]`, deliberately, because a workspace build compiles D-Star
   into the node too. Do not "simplify" it into a compile-time check.
4. **Secrets are connect/init arguments only.** Node secrets and portal
   passwords are never stored on a station, never placed in a snapshot, event
   or error, and never logged. `just cbindgen` fails the build if a
   secret-shaped field appears in an out-struct.

## Architecture rule

**Fat core, thin views.** Protocol, audio, codec and PTT logic lives in
`crates/`. The macOS and Iced clients are views over that engine. If you find
yourself writing protocol logic in Swift or in the Iced client, it is in the
wrong place — a feature implemented in the core reaches every platform, and one
implemented in a view reaches exactly one.

Per-platform UI should feel native to its platform. Same capability, same
concepts, not the same widgets.

## Before you open a pull request

Work on a branch, never directly on `main`.

The everyday gate:

```bash
just ci          # rustfmt + clippy (warnings are errors) + tests + C-header drift
```

The full gate, including the Swift side (needs a full Xcode on macOS):

```bash
just ci-full     # adds the FFI example, Python smoke, swift-format, AstarCore tests
```

Both must be green. If your change touches the C ABI, `just cbindgen`
regenerates `astar.h` / `astarserial.h` — commit the regenerated header with
the change that caused it, because the drift check will otherwise fail for the
next person.

Feature-gated code needs feature-gated checks. `dstar`, `ambe-hw`, `m17` and
`codec2-static` all have their own recipes and combinations; a plain
`cargo test --workspace` does not exercise them.

Tests are expected. A bug fix without a test that fails before it and passes
after is hard to accept, because nothing stops the bug coming back.

## Commit and PR conventions

* No AI or assistant attribution anywhere — not in commit messages, not in
  merge commits, not in PR descriptions, not in code comments, not in CI
  files. No `Co-Authored-By` trailers for tools, no "generated by".
* Write commit messages that explain *why*. The diff already says what.
* Never `git add -A`. Stage what you meant to change.
* Keep comments about intent and constraints, not narration. The existing code
  documents the reason a thing is the way it is — especially where the reason
  is a safety rule or a hard-won bug fix. Match that.

## Reporting bugs

Include the astar version (the popover footer on macOS, the window footer on
the Iced client), your OS and version, and what hardware is attached. For
anything involving audio, PTT or a dongle, say exactly which interface and
which USB device — "a CH340 cable" and "a UCI150" behave differently.

For anything protocol-shaped, a packet capture against a loopback or your own
node is worth a great deal more than a description. Do not attach captures that
contain credentials.
