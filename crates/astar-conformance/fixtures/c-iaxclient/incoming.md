# incoming.pcap (c-iaxclient)

Generated by `harness/asterisk_parity` (iax-7022) using the patched-C
iaxclient. The C client registers (as `astartest_notok`) and idles
waiting for an inbound NEW; the orchestrator triggers
`channel originate IAX2/astartest_notok application Wait,3` on the
Asterisk CLI ~3s after the harness starts.

Flow captured:
- REGREQ → REGAUTH → REGREQ+MD5 → REGACK (registration leg)
- NEW (inbound, from asterisk, dcallno=0) → CONNECT event in libiax2
- ACCEPT + ANSWER (we accept the call)
- PING from asterisk → PONG
- HANGUP from asterisk after Wait,3 completes
- ACK chain

## What this exercises

The NEW-received side of libiax2's FSM. Outbound captures (the four
deferred call scenarios — au:iax-c308) drive `iax_call`; this one drives
`iax_get_event` → `iax_accept` → `iax_answer`, the inbound path. The
Rust client's incoming-call work (au:iax-8baf) should match the state
transitions visible here.

Note: only libiax2's stderr is captured in the run log, not the on-wire
bytes from Asterisk's side — those are tshark'd directly from the
c_iaxclient netns and constitute the pcap.
